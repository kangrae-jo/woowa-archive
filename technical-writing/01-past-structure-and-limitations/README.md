# 1. 과거 구조와 아쉬움

## 결론

**채택:** 과거 구조는 직접 API 통신이 막힌 제약 안에서 DB를 작업 전달 통로로 사용한 단순 Polling 구조였다. 초기 장애 뒤 조회 대상을 별도 `prompt` 테이블로 분리하고 요청량을 제한했지만, 작업 상태와 처리 신뢰성은 명시적으로 다루지 못했다.

## 과거 구조

당시에는 AI 모델이 커서 AWS 프리 티어 서버에 올릴 수 없었다. 모델을 실행한 학교 컴퓨터의 권한 문제로 백엔드가 AI 서버에 이미지 생성 API를 호출하는 것도 불가능했다. 따라서 다음 흐름을 사용했다.

1. 백엔드가 `monster` 테이블에 사용자 `prompt`와 `image = null`인 행을 저장한다.
2. AI 워커가 N초마다 테이블 크기를 확인하고 `image = null`인 행을 조회한다.
3. AI 워커가 이미지를 생성해 Base64 형태로 같은 행의 `image`를 갱신한다.
4. 백엔드는 갱신된 `monster.image`를 조회해 결과를 제공한다.

즉, `monster` 테이블이 도메인 데이터 저장소이자 작업 큐 역할을 함께 맡았다. `image = null`은 대기 상태를 나타내는 암묵적 신호였다.

## 장애와 당시 보완

중간 발표에서 35명이 약 300개의 이미지 생성 요청을 보냈고 이미지 생성 기능이 정상 처리되지 않았다. 원문은 `image = null` 행을 찾는 선형 탐색과 이미지 생성 모델을 매번 로드한 구현을 주요 비용으로 설명한다.

이후 `prompt` 테이블을 별도 작업 큐처럼 추가했다. AI 워커는 이 테이블에서 프롬프트를 읽고 생성 결과를 `monster` 테이블에 기록했다. 프런트엔드는 연속 클릭을 막았고, 백엔드는 계정별 보유 수와 일일 생성 수를 제한했다. 최종 발표에서는 비슷한 요청량을 처리했지만 완료·유실·중복 건수는 기록되지 않았다.

## 현재 기준의 아쉬움

| 관심사 | 원문에서 확인한 내용 | 판단 |
| --- | --- | --- |
| 작업 상태 | `image = null` 또는 `prompt` 행의 존재로 대기를 표현 | 명시적 `PENDING`, `RUNNING`, `SUCCEEDED`, `FAILED` 상태가 없어 보완 대상 |
| 원자적 선점 | 워커가 조회한 작업을 선점하는 갱신·잠금 설명 없음 | 여러 워커가 같은 작업을 처리하지 않는다는 보장은 **확인 필요** |
| 워커 종료 복구 | 처리 도중 워커가 종료됐을 때의 만료 시각·복구 규칙 설명 없음 | 멈춘 작업을 다시 대기열로 돌리는 보장은 **확인 필요** |
| 재시도와 멱등성 | 실패 횟수, 재시도 한도, 중복 실행 시 결과 처리 규칙 설명 없음 | 무한 재처리와 중복 결과 방지 보장은 **확인 필요** |
| 결과 연결 | `monster id`와 `prompt id`를 보고 결과를 기록한다고 설명 | 명시적 연결 키와 제약 조건은 **확인 필요** |
| 검증 지표 | 비슷한 트래픽을 처리했다는 정성적 결과만 제시 | 완료·유실·중복 수를 분리한 정량 검증이 필요 |

조회 비용 개선과 요청 제한은 당시 장애 완화에는 유효했다. 다만 요청 제한은 작업 처리의 정확성을 보장하지 않으며, 별도 테이블을 만든 것만으로 큐의 선점·복구·재시도 성질이 생기지는 않는다.

과거 소스 코드와 SQL은 현재 저장소에서 확인되지 않았다. 위 항목은 실제 버그를 단정한 결과가 아니라, 원문에 보장 근거가 없는 지점을 다음 실패 테스트의 검증 대상으로 정리한 것이다.

## 다음 단계의 기준

외부 메시지 큐나 로드 밸런서는 도입하지 않는다. 동일한 제약을 유지한 최소 DB Polling 구현에서 중복 선점, 워커 종료, 결과 오연결을 먼저 재현한다.
