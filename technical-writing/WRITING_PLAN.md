## 문서 주제

외부 이미지 생성 워커 연동: DB Job Queue로 HTTP 요청과 작업을 분리하고 장애에 대응하기

## 대상 독자

- Spring Boot와 JPA로 REST API를 개발해 본 백엔드 개발자.
- 비동기 작업에서 작업 상태, 동시 선점, 타임아웃 복구, 재시도와 멱등성을 직접 다뤄 보고 싶은 사람.
- 비동기 처리를 구현하는 방식들을 알고 있으며, 서비스에 DB Job Queue 방식을 적용하는 과정이 궁금한 사람.

## 목차와 근거

### ① 문제: 어떤 문제가 있었나

커켓몬은 사용자가 입력한 프롬프트를 바탕으로 자신만의 몬스터 이미지를 생성하는 서비스였다. 약 300건의 이미지 생성 요청을 처리하던 중 시스템이 요청에 응답하지 못하는 장애를 경험했다.

당시 `Prompt` 테이블 분리와 요청 제한을 함께 적용한 뒤 비슷한 규모를 다시 처리할 수 있었다. 다만 변경 효과와 작업 유실·중복 여부는 측정하지 못했다.

이번 실험은 과거 장애 원인을 확정하는 것은 아니다. 과거와 유사한 구조에서 잠재적 신뢰성 문제 5가지를 재현하고, HTTP 요청 이후에도 작업을 보존할 방법을 검증한다.

이 글에서 다루는 5가지 문제는 다음과 같다.

1. Monster와 이미지 생성 Job의 등록 비원자성.
2. 여러 Worker의 동일 Job 중복 선점.
3. Worker 종료 이후 처리 중인 Job의 유실.
4. 생성 결과와 Monster의 잘못된 연결.
5. 한 작업의 실패로 인한 Scheduler 중단.

근거: [01. 과거 구조와 기록의 한계](./01-past-structure-and-limitations/README.md), [03. 잠재적 신뢰성 문제 재현](./03-failure-reproduction/README.md).

시각 자료: 과거 이미지 생성 구조와 당시 1차 대응 전후를 비교하는 아키텍처 그림.

### ② 비교한 방법: 어떤 방법들을 봤나

대안으로 `@Async`, Worker 직접 HTTP 호출, DB Job Queue, 메시지 브로커를 비교한다. 판단 기준은 작업 보존, 등록 원자성, 운영 비용이다. 외부 Worker가 웹 서버와 직접 통신할 수 없고 이미지 생성 시간을 예측하기 어렵다는 당시 제약을 유지한다.

하나의 DB를 공유하는 환경에서 도메인 데이터와 Job을 함께 저장할 수 있는 DB Job Queue를 선택한다. 메시지 브로커는 현재 규모와 운영 비용을 고려해 비범위로 둔다.

본문 작성 전 확인 필요: 당시 직접 통신이 불가능했던 구체적인 이유와 근거, 직접 HTTP 호출 대안의 호출 방향과 결과 전달 방식.

시각 자료: 네 가지 대안을 작업 보존·등록 원자성·운영 비용으로 비교한 표.

### ③ 해 본 일: 무엇을 해 봤나

웹 서버와 이미지 Worker를 별도 JVM으로 실행하고 MySQL만 공유하는 구조를 재구성한다. 먼저 최소 Polling 구조에서 앞서 제시한 5가지 문제를 재현한다.

개선 구조에는 `PENDING`, `RUNNING`, `SUCCEEDED`, `FAILED` 작업 상태를 추가한다. 조건부 UPDATE를 통한 원자적 선점, 처리 기한, 재시도, `claimToken`을 통한 오래된 결과 거부를 구현한다. 각 규칙은 실제 MySQL을 사용하는 통합 테스트로 검증한다.

이미지 생성은 지연을 주는 모의 Generator로 대체한다. Worker 종료에 따른 유실은 예외로 재현하고, 복구는 Worker가 응답하지 않는 `RUNNING` DB 상태를 만들어 검증한다. 이 테스트의 범위를 실제 JVM 종료·재시작 검증과 구분한다.

근거: [02. 최소 DB Polling 구조 재구성](./02-minimal-db-polling/README.md), [03. 잠재적 신뢰성 문제 재현](./03-failure-reproduction/README.md), [04. DB Job Queue 신뢰성 개선](./04-reliability-hardening/README.md), [05. 신뢰성 회귀 검증](./05-regression-verification/README.md).

시각 자료:

- Client → Web Server → MySQL ← Image Worker로 이어지는 최종 구조.
- `PENDING` → `RUNNING` → `SUCCEEDED`/`FAILED` 작업 상태 전이도. 실패·만료 후 재시도하는 `RUNNING` → `PENDING` 전이도 포함한다.
- Worker A의 기한 만료 후 Worker B가 재선점하고, A의 늦은 결과를 거부하는 시퀀스.

### ④ 달라진 점과 근거: 해 보니 무엇이 달라졌나

최소 구조에서 5가지 문제를 재현한 RED 테스트와 개선 구조의 GREEN 테스트를 비교한다. 다섯 GREEN 테스트가 모두 통과하는지 확인한 뒤 각 문제가 어떤 구현 규칙으로 해결됐는지 설명한다. 현재 검증 상태는 [05단계](./05-regression-verification/README.md#현재-검증-상태)를 참조한다.

**채택:** 별도 Web·Worker 환경에 HTTP 요청 300건을 입력하는 실제 측정을 기본 검증으로 수행한다. 기본 검증이 통과하면 요청 수 또는 HTTP 동시성을 늘려 추가 부하를 측정한다. 측정 통과 조건과 확대 기준은 [06단계](./06-final-300-job-measurement/README.md#측정-범위와-확대-기준)를 따른다.

기본 측정 결과는 접수, 완료, 실패, 미종결, 누락, 재시도, 전체 완료 시간을 요약한다. 추가 부하에서는 작업 대기 시간, 최대 PENDING, 재시도율과 전체 완료 시간의 변화를 비교한다. 실행 조건과 상세 결과는 측정 결과 파일에 보존하고 글에서 링크로 참조한다.

정상 부하 측정과 장애 복구 테스트가 서로 다른 근거라는 점을 구분한다. 모의 이미지 생성 조건에서 얻은 결과의 범위를 명시한다.

시각 자료:

- 5가지 문제의 RED 테스트와 GREEN 테스트 대응표.
- 300건 기본 측정의 접수·완료·실패·미종결·누락·재시도 결과 요약표.
- 기본 검증 통과 후 추가 부하 측정의 실행 조건과 결과 비교표.

### ⑤ 주의할 점: 언제 쓰면 위험한가

DB Polling은 작업 요청이 없어도 조회를 발생시키므로 Worker 수가 늘수록 DB 부하가 증가한다. `claimToken`은 오래된 결과 반영을 막지만 외부 이미지 생성의 중복 실행 자체는 막지 못한다. 처리 기한이 실제 생성 시간보다 짧으면 정상 작업도 만료와 재시도의 대상이 된다.

동시성 제한은 Worker 프로세스별로 적용되며, 요청이 처리 속도보다 빠르면 DB에 대기 작업이 계속 쌓인다. Polling 부하, 작업 대기 시간, 재시도율이 커지면 메시지 브로커를 포함한 다른 비동기 처리 방식을 다시 검토한다.

근거: [04. DB Job Queue 신뢰성 개선](./04-reliability-hardening/README.md), [06. 300건 기본 검증과 추가 부하 측정](./06-final-300-job-measurement/README.md).

시각 자료:

- 요청 유입 속도가 처리 속도보다 빠를 때 PENDING 작업이 증가하는 그래프.
- DB Job Queue 유지와 메시지 브로커 전환을 판단하는 지표 체크리스트.

## 용어

| 용어 | 이 문서에서의 의미 |
| --- | --- |
| 웹 서버, Web | 클라이언트의 HTTP 요청을 받아 Monster와 Job을 저장하고 작업 상태를 조회하는 Spring Boot 애플리케이션. 이미지 생성은 직접 실행하지 않는다. |
| 이미지 워커, Worker | DB에서 실행할 Job을 조회하고 이미지를 생성한 뒤 결과를 저장하는 별도 JVM 프로세스. HTTP 서버를 열지 않는다. |
| Job | 이미지 생성 요청 한 건의 상태와 실행 정보를 저장하는 단위. Monster와 연결되며 상태, 시도 횟수, 처리 기한 등을 가진다. |
| DB Job Queue | DB 테이블에 Job을 저장하고 이미지 워커가 Polling으로 가져가는 구조다. |
| 최소 구조 | 과거 구조와 유사하게 재구성한 기준 구현이다. 정상 상황에서는 동작하지만 작업 상태, 원자적 선점, 타임아웃, 재시도 등의 신뢰성 규칙은 없다. 과거 코드를 그대로 복원한 것은 아니다. |
| 개선 구조 | 최소 구조와 동일한 웹 서버·이미지 워커·MySQL 구성을 유지하면서 작업 상태, 원자적 선점, 타임아웃 복구, 재시도, 오래된 결과 거부를 추가한 구현이다. |
| Polling | 이미지 워커가 일정한 간격으로 DB를 조회해 실행할 Job을 찾는 방식이다. |
| 선점 | 특정 Job을 처리할 권한을 이미지 워커 하나가 획득하는 과정이다. 후보 조회만으로는 선점되지 않으며 조건부 UPDATE 성공으로 결정한다. |
| 처리 기한 | RUNNING 상태인 Job의 현재 선점이 유효한 시간이다. 기한이 지나면 복구 대상이 된다. |
| claimToken | 선점할 때마다 새로 발급하는 식별자다. 현재 token과 일치하는 이미지 워커만 결과를 반영할 수 있다. |
| RED 테스트 | 최소 구조가 원하는 신뢰성 조건을 지키지 못한다는 사실을 재현하는 테스트다. |
| GREEN 테스트 | 개선 구조가 같은 신뢰성 조건을 지킨다는 사실을 검증하는 테스트다. |
