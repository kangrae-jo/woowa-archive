# ⑦ 이미지 생성 요청 1,500건의 추가 부하 검증

300건 기본 검증을 마친 뒤 요청 수를 5배인 1,500건으로 늘려 추가 부하를 확인했습니다. 3분 동안 요청을 투입한 결과 접수 응답의 p95는 18ms였고 전체 작업은 15분 56.456초에 모두 성공했습니다. 접수한 작업의 유실과 결과 오연결은 발견되지 않았습니다.

## 1,500건을 3분 동안 투입한 조건

이번에는 작업 처리 속도보다 빠르게 요청을 접수한 뒤 DB에 쌓인 작업이 모두 완료되는지 살펴봤습니다. Worker 동시 처리 상한은 8, 작업당 모의 생성 지연은 5초로 유지했습니다. 웹 서버, Worker와 측정 프로그램은 별도 JVM으로 실행하고 새 임시 MySQL의 빈 측정 전용 DB를 사용했습니다.

요청은 120ms마다 한 건씩 초당 약 8.33건을 보내도록 했습니다. 앞선 요청의 응답을 받은 뒤 기다리는 방식으로는 응답 지연에 따라 투입량이 줄어들 수 있으므로 기준 시각에 요청별 간격을 더해 전송을 예약했습니다. HTTP 등록 동시 실행 상한은 기존과 같은 35로 뒀습니다.

3분은 요청을 넣는 구간입니다. 동시 처리 8건과 모의 생성 5초를 기준으로 계산한 이상적인 처리율은 초당 1.6건이므로 전체 완료는 시작 후 20분까지 확인하기로 했습니다. 접수 응답에는 p95 500ms 이하를 이번 실험의 통과 기준으로 정했습니다. 운영 서비스의 응답 목표를 검증한 기준은 아닙니다.

## 접수 p95 18ms와 1,500건 전체 성공

2026년 11월 1일 실행에서 첫 요청은 측정 시작 후 0.006613초, 마지막 요청은 179.893841초에 시작했습니다. 예정한 1,500건이 모두 180초 구간 안에 전송됐고 다음 조건을 통과했습니다.

| 확인 항목 | 통과 기준 | 실제 결과 |
| --- | --- | --- |
| 접수 | HTTP 202 응답 1,500건 | 1,500건 |
| 접수 응답 시간 | `POST /jobs` p95 500ms 이하 | 18ms |
| 전체 완료 | 시작 후 20분 이내 성공 1,500건 | 15분 56.456초에 모두 성공 |
| 접수 오류와 중복 Job ID | 각각 0건 | 각각 0건 |
| 실패, 미종결과 유실 | 각각 0건 | 각각 0건 |
| 결과 오연결과 이미지 없는 성공 | 각각 0건 | 각각 0건 |

재시도 Job과 추가 선점도 각각 0건이었습니다. 작업별 CSV 1,500행의 ID, 상태, 이미지와 백분위수 등을 독립적으로 다시 계산한 36개 대조 항목이 모두 일치했습니다. DB에서도 Job과 Monster 및 성공 결과가 각각 1,500건이고 결과 이미지가 해당 프롬프트와 연결된 것을 확인했습니다. 원본과 판정 과정은 [이번 실행 기록](../06-final-300-job-measurement/results/1e8aec76-1ca1-4c51-9501-d7da0b9a5591/README.md)에 남겼습니다.

## 접수 이후 이어진 작업 대기

접수는 빨랐지만 작업이 바로 완료된 것은 아닙니다. 관측한 최대 대기 작업 수는 1,212건이었고 작업 대기 시간의 p95는 734.125초였습니다. 작업 처리 시간의 p95는 5.014초였구요. 요청이 들어오는 동안에는 생성 작업이 쌓였고 투입을 마친 뒤 대기열을 처리했습니다.

| 항목 | 300건 기본 검증 | 1,500건 추가 검증 |
| --- | --- | --- |
| 투입 방식 | 동시 실행 상한 35로 일괄 전송 | 상한 35, 120ms 간격으로 전송 |
| Worker와 모의 생성 | 동시 처리 8건, 작업당 5초 | 동시 처리 8건, 작업당 5초 |
| HTTP 접수 p95 | 160ms | 18ms |
| 작업 대기 p95 | 178.087초 | 734.125초 |
| 관측 최대 대기 작업 | 295건 | 1,212건 |
| 전체 완료 시간 | 193.639초 | 956.456초 |

이번에는 요청 수와 투입 방식을 함께 바꿨습니다. 그래서 접수 p95가 낮아진 차이를 성능 개선의 효과로 해석하지는 않습니다. 최대 대기 작업 수 역시 1초 간격의 관찰값이며 순간 최대값을 보장하지 않습니다. 설정과 상세 지연 수치는 [추가 측정 결과](../06-final-300-job-measurement/README.md#1500건-추가-부하-측정-결과)를 참조합니다.

이번 실행에서는 로컬 모의 생성 조건에서 처리 속도보다 빠르게 들어온 1,500건을 보존하고 모두 완료한 것을 확인했습니다. 실제 AI 모델의 처리 성능이나 최대 처리 용량, 처리 도중 Worker를 종료하고 재시작하는 복구는 확인하지 않았습니다. 운영에 적용할 때는 접수 응답 시간과 함께 사용자가 결과를 기다릴 수 있는 시간을 정하고 그 기준에 맞춰 동시 처리 상한과 접수 제한을 검토해야 합니다.
