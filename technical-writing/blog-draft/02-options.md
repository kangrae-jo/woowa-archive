# ② 비교한 방법: 어떤 방법들을 봤나요?

이미지 생성 작업을 웹 요청과 분리하는 방법은 여러 가지입니다. 이번에 확인하려는 조건은 웹 서버가 요청을 접수한 뒤에도 작업을 보존하고, 도메인 데이터와 생성 요청을 함께 등록하는 것입니다. 이를 기준으로 `@Async`, Worker 직접 HTTP 호출, DB Job Queue, 메시지 브로커를 비교했습니다.

## 비교 기준을 먼저 정했습니다

첫 번째 기준은 작업 보존입니다. 웹 서버나 Worker가 멈추더라도 접수한 작업을 다시 찾을 수 있어야 합니다. 두 번째는 등록 원자성입니다. Monster만 저장되고 생성 작업이 등록되지 않는 상태를 막아야 합니다. 세 번째는 운영 비용입니다. 작업을 전달하기 위해 추가할 서버와 관리할 규칙이 어느 정도인지 살펴봤습니다.

실험에서는 웹 서버와 Worker가 직접 HTTP로 통신하지 않고 DB만 공유하는 조건을 유지했습니다. 이미지 생성 시간도 HTTP 요청의 대기 시간으로 묶지 않습니다. 다만 당시 직접 통신이 불가능했던 구체적인 네트워크 구성과 이유는 확인이 필요합니다. 현재 Worker가 HTTP 서버를 열지 않는 설정은 이번 재구성의 구현 조건입니다.

| 방식 | 작업 보존 | Monster와 작업의 등록 원자성 | 운영 비용·제약 |
| --- | --- | --- | --- |
| 별도 작업 저장소 없는 `@Async` | 실행 요청을 DB에 남기는 규칙이 별도로 필요합니다. | 비동기 실행 제출만으로 두 등록을 함께 커밋하지는 않습니다. | 추가 서버는 적지만 웹 프로세스의 실행 풀과 예외 처리를 관리해야 합니다. |
| Web → Worker 직접 HTTP 호출 | Worker의 영속 접수와 접수 실패 처리 규칙이 필요합니다. | DB 저장과 원격 호출 사이의 실패를 처리해야 합니다. | Worker의 HTTP API와 타임아웃·접수 확인 규칙이 필요합니다. |
| DB Job Queue | 접수한 작업을 DB 행으로 남깁니다. | 같은 DB의 Monster와 Job을 한 트랜잭션으로 저장할 수 있습니다. | 기존 DB를 사용하며 Polling·선점·복구 규칙을 직접 구현합니다. |
| 메시지 브로커 | 영속화와 전달·처리 확인 설정을 함께 설계합니다. | 도메인 저장과 메시지 발행 사이의 실패를 다루는 설계가 필요합니다. | 별도 브로커와 발행·소비·재전송 운영을 관리해야 합니다. |

이 표는 각 방식의 기본 구성과 추가해야 할 규칙을 비교한 것입니다. 처리량을 측정한 결과는 아닙니다.

## 실행을 넘기는 것과 작업을 남기는 것을 구분했습니다

Spring의 `@Async`는 메서드 실행을 `TaskExecutor`에 제출하고 호출자가 먼저 반환하도록 합니다. 따라서 별도 저장 규칙 없이 `@Async`만 붙이는 구성은 이번 작업 보존 요구를 충족하지 못한다고 판단했습니다. **거부:** 작업 저장소 없는 `@Async` 단독 구성을 이번 실험의 기반으로 사용하지 않습니다. [Spring의 비동기 실행 설명](https://docs.spring.io/spring-framework/reference/integration/scheduling.html)

직접 HTTP 호출은 Web이 Worker의 생성 API를 호출하는 방식으로 비교했습니다. Worker가 접수 후 먼저 응답하더라도 접수한 작업을 어디에 남길지, 응답이 끊겼을 때 Web이 무엇을 재시도할지 정해야 합니다. **거부:** 직접 HTTP 통신을 사용하지 않는 이번 실험 조건에서는 이 방식을 선택하지 않습니다.

메시지 브로커를 사용하면 작업 전달을 별도 인프라에 맡길 수 있습니다. 예를 들어 RabbitMQ에서는 발행자가 브로커의 수신을 확인하는 publisher confirm과 소비자의 처리 완료를 확인하는 acknowledgement를 구분합니다. 이 기능들을 포함한 전달 보장과 도메인 저장의 연계를 설계해야 합니다. [RabbitMQ의 확인 응답 설명](https://www.rabbitmq.com/docs/confirms)

**비범위:** 이번 실험에서는 메시지 브로커를 구축하지 않습니다. 현재 사용할 수 있는 하나의 DB에서 작업 등록과 실행 규칙을 검증하는 데 범위를 둡니다. 이 선택은 DB Job Queue가 브로커보다 빠르거나 항상 운영하기 쉽다는 판단을 뜻하지 않습니다.

## 같은 DB의 트랜잭션을 사용할 수 있는 방식을 선택했습니다

**채택:** Monster와 Job을 같은 DB에 등록하는 DB Job Queue를 사용합니다. 웹 서버는 두 데이터를 함께 저장한 뒤 접수 결과를 반환하고, Worker는 DB에 남은 Job을 읽습니다. 웹 서버의 메모리나 Worker와의 직접 호출에 실행 요청을 맡기지 않아도 됩니다.

대신 DB를 사용한다는 이유만으로 신뢰성이 생기지는 않습니다. 어느 Worker가 실행할지, 처리 중 멈춘 작업을 언제 복구할지, 뒤늦게 도착한 결과를 받아들일지 직접 정해야 합니다. 다음 장에서는 이 규칙을 최소 구조에 하나씩 추가한 과정을 설명합니다.
