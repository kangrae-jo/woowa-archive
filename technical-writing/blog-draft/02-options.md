# ② 비동기 처리 방법 4가지 비교와 DB Job Queue 선택

이번 실험에서는 이미지 생성 작업을 DB에 저장하고 Worker가 Polling으로 가져가는 DB Job Queue를 선택했습니다. 웹 서버와 Worker가 하나의 MySQL을 공유하는 조건에서, `Monster`와 Job을 같은 트랜잭션으로 등록할 수 있기 때문입니다.

이 방식을 선택하기까지 `@Async`, Worker 직접 HTTP 호출, DB Job Queue, 메시지 브로커를 비교했습니다. 기준은 작업 보존, 등록 원자성, 운영 비용이었습니다.

## 작업 보존·등록 원자성·운영 비용을 기준으로 비교

웹 서버는 이미지 생성이 끝날 때까지 기다리는 대신, 작업을 등록한 뒤 접수 결과를 먼저 반환하도록 했습니다. 이때 요청에 먼저 응답하는 것뿐 아니라, 응답한 뒤에도 접수한 작업을 다시 찾을 수 있어야 했습니다.

그래서 다음 세 가지를 기준으로 각 방식을 살펴봤습니다.

1. 작업 보존: 웹 서버나 Worker가 멈추더라도 접수한 작업을 다시 찾을 수 있는가.
2. 등록 원자성: `Monster`와 Job을 함께 저장하거나 함께 취소해, 생성 작업이 없는 `Monster`가 남는 상황을 막을 수 있는가.
3. 운영 비용: 추가할 인프라와 애플리케이션에서 직접 관리해야 할 규칙은 무엇인가.

실험에서는 [기존 프로세스 구성](../README.md#application-구조)을 유지해, 웹 서버와 Worker가 직접 HTTP로 통신하지 않고 MySQL만 공유하도록 했습니다. 다만 당시 직접 통신이 불가능했던 구체적인 네트워크 구성과 이유는 확인이 필요합니다. 현재 Worker가 HTTP 서버를 열지 않는 것은 이번 재구성에서 정한 구현 조건입니다.

| 방식 | 작업 보존 | Monster·Job 등록 시 고려할 점 | 운영 비용 | 이번 판단 |
| --- | --- | --- | --- | --- |
| 별도 작업 저장소 없는 `@Async` | 영속 저장·복구 규칙 추가 필요 | 비동기 실행 제출만으로 등록 원자성을 보장하지 않음 | 실행 풀·예외 처리 관리 | 거부 |
| 웹 서버 → Worker 직접 HTTP 호출 | Worker의 영속 접수 필요 | DB 저장과 원격 접수 사이의 실패 처리 필요 | HTTP API·타임아웃·재시도 관리 | 거부 |
| DB Job Queue | DB 행으로 작업 보존 | 같은 DB 트랜잭션으로 함께 저장 가능 | Polling·선점·복구 규칙 구현 | 채택 |
| 메시지 브로커 | 영속화·전달 확인 설계 필요 | DB 저장과 메시지 발행 사이의 실패 처리 필요 | 브로커·발행·소비·재전송 관리 | 비범위 |

표의 판단은 이번 실험 조건을 기준으로 내렸습니다. 구성 요소와 필요한 규칙을 비교했으며, 방식별 처리량은 측정하지 않았습니다.

## @Async: 실행 요청을 보존할 규칙이 필요

Spring의 `@Async`는 메서드 실행을 `TaskExecutor`에 제출하고, 호출자가 먼저 반환하도록 합니다. 웹 서버 안에서 이미지 생성을 비동기로 실행하면 별도의 작업 전달 서버 없이 HTTP 응답과 생성 작업의 실행을 분리할 수 있습니다. [Spring의 비동기 실행 설명](https://docs.spring.io/spring-framework/reference/integration/scheduling.html#scheduling-annotation-support-async)

다만 실행 요청을 메모리에만 두면 웹 프로세스가 종료됐을 때 복구할 작업을 찾을 수 없습니다. 접수한 작업을 다시 처리하려면 DB 등에 실행 요청을 남기고, 미완료 작업을 다시 읽는 규칙이 필요합니다.

이번에는 작업 보존을 기본 조건으로 삼았으므로, 별도 작업 저장소 없는 `@Async` 단독 구성은 선택하지 않았습니다.

## 직접 HTTP 호출: 원격 접수 실패와 재시도 처리 필요

직접 HTTP 호출은 웹 서버가 Worker의 생성 API를 호출하는 방식으로 비교했습니다. Worker가 작업을 접수한 뒤 먼저 응답하도록 구성하면, 웹 요청이 이미지 생성 완료까지 기다리지 않게 할 수 있습니다.

이때도 Worker가 접수한 작업을 어디에 저장할지 정해야 합니다. 예를 들어 Worker가 작업을 접수했지만 응답이 웹 서버에 도착하지 않는다면, 웹 서버에서는 실제 접수 여부를 알기 어렵습니다. 재시도할 때 같은 작업을 중복 접수하지 않도록 할 규칙도 필요하겠죠.

`Monster` 저장에 성공한 뒤 Worker 접수에 실패하는 상황도 다뤄야 합니다. 이런 접수·복구 규칙에 더해, 두 프로세스가 직접 HTTP로 통신하지 않는 이번 실험 조건을 고려해 이 방식은 제외했습니다.

## 메시지 브로커: 작업 전달 인프라와 DB 저장의 연계 필요

메시지 브로커를 사용하면 웹 서버는 생성 요청을 메시지로 발행하고, Worker는 그 메시지를 받아 실행하도록 구성할 수 있습니다. 작업 전달을 별도 인프라에 맡길 수 있다는 장점이 있습니다.

예를 들어 RabbitMQ는 발행자가 브로커의 수신을 확인하는 publisher confirm과, 소비자가 메시지를 받아 처리했음을 브로커에 알리는 consumer acknowledgement를 구분합니다. 브로커가 메시지를 받았는지와 Worker가 처리를 마쳤는지는 각각 확인해야 하는 단계입니다. [RabbitMQ의 확인 응답 설명](https://www.rabbitmq.com/docs/confirms)

브로커를 사용하더라도 `Monster`를 DB에 저장한 뒤 메시지 발행에 실패하는 상황은 다뤄야 합니다. 별도 브로커를 운영하고 메시지의 영속화·재전송 규칙을 설정하는 비용도 추가됩니다.

이번에는 기존 MySQL 안에서 작업 등록과 실행 규칙을 검증하는 데 범위를 두고, 메시지 브로커 구축은 비범위로 뒀습니다.

## DB Job Queue: 같은 트랜잭션으로 Monster와 Job 등록

DB Job Queue에서는 웹 서버가 `Monster`와 Job을 같은 DB에 저장합니다. 두 등록을 하나의 트랜잭션으로 묶으면 Job 저장이 실패했을 때 `Monster` 저장도 함께 롤백할 수 있습니다. 현재 구현에서는 [JobRegistrationService.request()](../04-reliability-hardening/src/main/java/com/kng0501/dbqueue/server/application/JobRegistrationService.java)에 이 트랜잭션 경계를 뒀습니다.

등록 트랜잭션이 커밋되면 웹 서버는 접수 결과를 반환하고, Worker는 DB에 남은 Job을 Polling으로 조회합니다. 기존 MySQL을 사용하면서 작업 등록과 실행을 분리할 수 있다는 점이 이번 선택의 이유였습니다.

대신 Polling으로 발생하는 DB 조회와 작업 처리 규칙은 직접 관리해야 합니다. 여러 Worker 중 누가 Job을 실행할지, 실행 중 멈춘 작업을 언제 복구할지, 뒤늦게 도착한 결과를 받아들일지까지 정해야 했습니다.
