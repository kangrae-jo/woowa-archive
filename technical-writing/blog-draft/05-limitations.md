# ⑤ DB Job Queue의 보장 범위와 운영 전 확인할 제약

이번 실험에서는 웹 서버와 Worker가 MySQL만 공유하는 구조를 유지하면서 작업 보존, 선점, 복구와 결과 반영 규칙을 검증했습니다. 운영에 적용하려면 이 규칙의 보장 범위와 함께 DB 조회 비용, 실제 이미지 생성 시간, 처리할 수 있는 작업량을 확인해야 합니다.

④에서 확인한 300건의 정상 완료를 기준으로, 현재 구현에 남아 있는 제약과 다음에 살펴볼 지표를 정리하겠습니다.

## 작업이 없어도 발생하는 Polling과 보존 비용

Worker는 실행 여유가 있을 때 DB에서 처리할 후보를 찾고, 복구 작업은 처리 기한이 지난 Job을 주기적으로 조회합니다. 두 조회의 기본 간격은 각각 100ms입니다. 처리할 작업이 없어도 조회가 발생하며, Worker 프로세스를 추가하면 각 프로세스가 같은 DB를 조회합니다.

Polling 간격을 줄이면 새 작업을 더 자주 확인할 수 있지만 조회 횟수가 늘어납니다. Worker를 늘릴 때도 같은 후보를 두고 경쟁하는 비용을 함께 봐야 합니다.

이번 [스키마](../04-reliability-hardening/src/main/resources/db/04/schema.sql)에는 대기 작업과 만료 작업을 찾기 위한 인덱스를 뒀습니다. 완료·실패 Job도 검증을 위해 보존하므로 데이터는 계속 쌓입니다. 운영에서는 조회 횟수와 실행 시간, 누적 행 수를 관찰하고 보존 기간과 정리 방식을 따로 정해야 합니다.

## 같은 Job의 결과 반영과 이미지 생성 호출의 보장 범위

`claimToken`은 선점할 때마다 새로 발급하는 실행 식별자입니다. 같은 Job을 다시 선점하면 이전 token의 완료 요청을 거부해, 늦게 도착한 결과가 현재 결과를 덮어쓰지 않도록 했습니다. 구체적인 반영 조건은 [JobQueue의 완료 처리](../04-reliability-hardening/src/main/java/com/kng0501/dbqueue/worker/application/JobQueue.java)에서 확인할 수 있습니다.

다만 처리 기한이 만료돼도 기존 Generator 호출이 자동으로 끝나지는 않습니다. 이전 실행이 계속되는 동안 다른 Worker가 재선점하면 두 실행의 이미지 생성 호출이 겹칠 수 있습니다. **현재 규칙이 제한하는 범위는 같은 Job의 DB 결과 반영입니다.** 외부 이미지 생성 호출이 정확히 한 번 발생한다는 보장은 하지 않습니다.

HTTP 요청의 중복 접수도 별도로 봐야 합니다. 같은 프롬프트로 요청을 두 번 보내면 [현재 등록 구현](../04-reliability-hardening/src/main/java/com/kng0501/dbqueue/server/application/JobRegistrationService.java)은 각각 새로운 `Monster`와 Job을 만듭니다. 같은 요청인지 식별해 하나로 처리하는 멱등성 키는 구현하지 않았습니다.

## 처리 기한·재시도와 실행 자원 반환의 구분

처리 기한이 실제 생성 시간보다 짧으면 정상적으로 진행 중인 작업도 만료될 수 있습니다. 이를 재시도하면 이미지 생성 호출과 비용이 추가로 발생할 수 있죠. 반대로 기한을 길게 잡으면 응답하지 않는 작업을 복구하기까지 더 오래 기다립니다.

이번 실험에서는 작업당 5초를 기다리는 모의 생성기에 처리 기한 30초를 적용했습니다. 재시도 간격은 1초, 최대 선점 횟수는 최초 선점을 포함해 3회로 뒀습니다. 이 값은 실험 조건으로 정했으며, 운영에 적절한지는 실제 생성 시간 분포와 실패 유형을 보고 확인해야 합니다. 기본 설정은 [application.yml](../src/main/resources/application.yml)에서 관리합니다.

현재는 작업이 진행 중임을 주기적으로 알리고 처리 기한을 연장하는 기능이 없습니다. 실패가 반복될수록 재시도 간격을 늘리거나, 재시도 시점을 무작위로 분산하는 기능도 넣지 않았습니다. 여러 작업이 비슷한 시점에 실패하면 재시도가 몰릴 수 있으므로, 외부 생성 서버에 가해지는 부하도 확인해야 합니다. [AWS의 타임아웃·재시도·백오프·지터 설명](https://aws.amazon.com/builders-library/timeouts-retries-and-backoff-with-jitter/)

DB 상태를 복구하는 것과 실행 자원이 반환되는 것도 구분해야 합니다. [JobScheduler](../04-reliability-hardening/src/main/java/com/kng0501/dbqueue/worker/application/JobScheduler.java)는 실행 작업이 끝날 때 동시 실행 자리를 반환합니다. 따라서 생성 호출이 응답하지 않고 계속 남아 있으면, Job을 `PENDING`으로 돌려도 그 호출이 차지한 실행 자리는 반환되지 않습니다. 실제 생성 API를 연결할 때는 호출의 타임아웃과 취소 동작이 실행 자원을 반환하는지도 별도 확인이 필요합니다.

## Worker별 실행 상한과 DB에 쌓이는 대기 작업

동시 처리 상한은 Worker 프로세스 하나가 한 번에 실행할 수 있는 작업 수입니다. 예를 들어 각 Worker가 최대 8개씩 실행하도록 설정하고 프로세스 두 개를 띄우면, 전체에서는 최대 16개가 실행될 수 있습니다. 현재 구현에는 여러 프로세스를 합친 전역 상한이 없습니다.

④의 300건 측정에서는 Worker 프로세스 하나가 최대 8개를 동시에 실행하고, 각 작업은 테스트 코드에서 5초를 기다리도록 했습니다. 항상 8개가 실행되고 모든 작업이 정확히 5초 걸린다고 가정하면, 생성 단계의 평균 처리율은 `8 ÷ 5 = 1.6건/초`로 계산할 수 있습니다. 이 값에는 DB 처리와 스케줄링 시간이 들어 있지 않으며, 실제 측정 결과와 구분해야 합니다.

이보다 빠르게 작업이 계속 들어오면 대기 작업이 쌓입니다. 현재 등록 경로에는 대기 중인 Job 수를 기준으로 접수를 제한하는 로직도 없습니다. 작업을 DB에 남기면서도, 사용자가 결과를 받기까지의 시간은 계속 길어질 수 있습니다.

[300건 측정](./04-results.md)에서도 HTTP 등록 응답의 p95는 160ms였지만, 작업 대기의 p95는 178.087초였습니다. 관측한 최대 `PENDING`은 295건이었구요. 요청을 접수하는 시간과 실제 작업이 끝날 때까지의 시간을 함께 봐야 하는 이유입니다.

## 관측 지표에 따른 DB Job Queue 유지와 재검토

이번 실험에서는 도메인 데이터와 Job을 같은 트랜잭션으로 등록할 수 있는 DB Job Queue를 유지했습니다. 앞으로는 다음 지표를 관찰하면서 현재 구현을 조정할지, 작업 전달 방식을 바꿀지 판단하려고 합니다. 표는 추가 검증의 기준이며, 모든 현상이 이번 실행에서 관측됐다는 뜻은 아닙니다.

| 관측할 현상 | 다시 확인할 항목 |
| --- | --- |
| 작업이 적어도 DB 조회량과 조회 시간이 큼 | Polling·복구 간격, 인덱스, 누적 Job 수와 Worker 수 |
| 대기 시간·PENDING·미종결 작업이 계속 증가 | 요청 유입, 실제 생성 시간, 동시 처리 상한과 접수 제한 |
| 정상 작업의 만료와 재시도가 잦음 | 생성 시간 분포, 처리 기한, 실패 유형과 재시도 간격 |
| 같은 후보의 선점 경쟁이 잦음 | 후보 조회 순서, 선점 성공률과 작업 분배 방식 |
| 작업 전달을 업무 DB에서 분리할 필요가 생김 | 메시지 브로커의 전달·재전송 규칙과 추가 운영 비용 |

메시지 브로커를 선택할 때도 이미지 생성의 처리 용량과 중복 전달에 대응할 규칙은 함께 설계해야 합니다. 예를 들어 RabbitMQ의 신뢰성 문서도 장애 뒤 재전송·재전달이 발생할 수 있으므로 소비자의 중복 제거 또는 멱등 처리가 필요하다고 설명합니다. [RabbitMQ의 신뢰성 가이드](https://www.rabbitmq.com/docs/reliability)

우선은 [추가 측정 기준](../06-final-300-job-measurement/README.md#측정-범위와-확대-기준)에 따라 Worker의 실행 상한과 모의 생성 지연을 유지한 채 총 요청 수를 늘려보려고 합니다. 300건을 넘는 추가 부하 측정은 아직 실행하지 않았습니다. 작업 대기 시간과 최대 `PENDING`, 전체 완료 시간이 어떻게 달라지는지 확인하고, 그 결과를 기준으로 현재 방식을 어디까지 유지할지 판단하겠습니다.
