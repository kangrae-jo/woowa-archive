# ⑤ 주의할 점: 언제 쓰면 위험한가요?

DB Job Queue를 선택하면 접수한 작업과 처리 상태를 같은 DB에서 관리할 수 있습니다. 이번 구현에서는 그 위에 선점과 복구, 결과 반영 규칙을 추가했습니다. 다만 이 규칙이 보장하는 범위와 처리 용량의 한계를 함께 봐야 합니다.

## Polling 비용은 작업이 없어도 발생합니다

Worker는 실행 여유가 있을 때 DB에서 후보를 찾고, 복구 작업은 만료된 Job을 주기적으로 조회합니다. 처리할 작업이 없어도 조회가 발생합니다. Worker 수를 늘리거나 Polling 간격을 줄이면 조회 빈도와 같은 후보에 대한 경합이 늘 수 있습니다.

작업을 DB에 보존하는 만큼 준비·만료 조회 인덱스와 테이블의 보존 기간도 관리해야 합니다. 이번 구현은 완료·실패 Job도 검증을 위해 남깁니다. 테이블을 분리했다는 이유만으로 누적 데이터가 작아지거나 조회 비용이 항상 낮아진다고 가정하지 않습니다.

## claimToken은 외부 생성의 중복 실행을 막지 않습니다

처리 기한이 지났다고 이전 Generator가 자동으로 멈추지는 않습니다. 이전 실행이 계속되는 동안 다른 Worker가 같은 Job을 재선점할 수 있습니다. claimToken은 그중 어떤 실행의 결과를 DB에 반영할지 판단합니다. **이미지 생성 호출이 정확히 한 번 발생한다는 보장은 하지 않습니다.**

범위는 동일한 `job_id`입니다. 같은 프롬프트로 HTTP 요청을 두 번 보내면 이번 등록 구현은 각각 새로운 Monster와 Job을 만듭니다. 요청 자체의 중복 접수를 막는 멱등성 키는 구현하지 않았습니다. 프론트 디바운스와 하루 생성 제한의 효과를 이 결과 반영 규칙에 포함하지 않습니다.

## 처리 기한과 재시도는 생성 시간에 맞춰야 합니다

처리 기한이 실제 생성 시간보다 짧으면 정상 작업도 만료됩니다. 이런 작업을 재시도하면 외부 생성의 중복 실행과 추가 비용이 생길 수 있습니다. 기한이 너무 길면 응답하지 않는 실행을 복구하기까지 오래 기다립니다.

이번 실습의 기본 처리 기한은 30초이고, 모의 생성 지연은 5초입니다. 재시도 간격은 고정 1초이며 최대 시도는 최초 실행을 포함해 3회입니다. 이 값은 관찰용 설정이며 운영 적정값을 측정한 결과가 아닙니다. 실행 중 기한을 연장하는 Heartbeat와 재시도 backoff·jitter도 현재 구현에는 없습니다. 설정의 단일 기준은 [application.yml](../src/main/resources/application.yml)입니다.

## Worker를 늘려도 전체 용량을 따로 확인해야 합니다

동시성 상한은 Worker JVM 하나에 적용됩니다. 예를 들어 각 Worker의 상한이 8이고 프로세스가 두 개라면 전체에서 최대 16개를 동시에 실행할 수 있습니다. 이번 구현은 여러 프로세스 전체의 전역 상한을 제공하지 않습니다.

요청 유입이 처리 속도보다 빠른 동안에는 대기 작업이 쌓입니다. 측정 계획처럼 Worker 한 프로세스의 동시 실행이 8이고 작업당 모의 생성이 5초라면, DB 처리 시간을 제외한 생성 처리율의 계산상 상한은 초당 약 1.6건입니다. 이보다 빠르게 작업이 계속 들어오면 대기가 증가합니다. 이는 설정을 설명하기 위한 계산이며 실측 처리량은 아닙니다.

따라서 HTTP 접수가 빠르게 끝났다는 결과와 이미지 작업이 제때 끝났다는 결과를 함께 봐야 합니다. 최대 PENDING과 대기 시간, 미종결 수, 재시도율을 관찰하고 실행 조건을 결과와 함께 남깁니다.

## 관측 결과를 기준으로 처리 방식을 다시 검토합니다

**유지:** 현재는 같은 DB에 도메인과 Job을 등록할 수 있는 조건에서 DB Job Queue의 처리 규칙을 검증합니다. 다음 현상이 반복되면 구현과 다른 처리 방식을 함께 검토합니다.

| 관측할 현상 | 다시 검토할 항목 |
| --- | --- |
| 작업이 적어도 DB 조회 부하가 큽니다. | Polling·복구 간격, 인덱스, Worker 수와 알림 방식입니다. |
| 대기 시간과 미종결 작업이 계속 증가합니다. | 생성 처리 용량과 요청 유입, 동시성 배치입니다. |
| 정상 작업의 만료와 재시도가 잦습니다. | 생성 시간 분포와 처리 기한, 재시도 간격입니다. |
| 여러 Worker의 선점 경합이 커집니다. | 후보 조회·선점 방식과 작업 분배 구조입니다. |
| 작업 전달을 별도 인프라로 관리할 필요가 생깁니다. | 메시지 브로커를 포함한 다른 비동기 처리 방식입니다. |

이 항목들은 관측할 지표와 검토 대상을 연결한 것입니다. 브로커로 바꾸면 생성 처리 용량이나 결과 멱등성이 자동으로 해결된다고 판단하지 않습니다. 현재 결과로 확인한 조건부터 기록하고, 그 범위를 넘어서는 요구가 생길 때 다음 선택을 검토합니다.
