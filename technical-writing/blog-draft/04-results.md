# ④ 신뢰성 회귀 테스트 5건 통과와 작업 300건 처리 결과

개선 구조는 MySQL 통합 테스트에서 다섯 가지 신뢰성 조건을 모두 통과했습니다. 모의 Generator를 사용하고 웹 서버와 Worker를 별도 JVM으로 실행한 정상 부하 측정에서도 이미지 생성 작업 300건을 모두 완료했고, 전체 완료 시간은 193.639초였습니다.

③에서 추가한 규칙이 어떤 상황에서 동작하는지 확인하기 위해, 실패를 제어하는 테스트와 실제 프로세스를 나눈 정상 부하 측정을 각각 수행했습니다. 먼저 같은 다섯 조건에서 최소 구조와 개선 구조를 비교하고, 이어서 300건을 접수한 뒤 작업이 어떻게 처리됐는지 살펴보겠습니다.

## 같은 다섯 조건으로 최소 구조와 개선 구조 비교

최소 구조에서는 지켜야 할 신뢰성 조건을 검증문(assertion)으로 작성하고, 이 검증이 실패하는 상황을 재현했습니다. 이를 RED 테스트라고 부릅니다. 개선 구조에서는 대응하는 조건을 다시 검사하는 GREEN 회귀 테스트를 작성했습니다.

RED에서는 의도한 검증문이 실패했는지를 확인했습니다. DB 연결이나 Spring Context 초기화에서 실패했다면, 원하는 문제를 재현했다고 볼 수 없기 때문입니다. [최소 구조의 실패 재현 기록](../03-failure-reproduction/README.md)에서는 다섯 테스트가 각각의 검증문에서 실패한 것을 확인했습니다.

| 신뢰성 조건 | 최소 구조의 실패 재현 | 개선 구조의 회귀 검증 |
| --- | --- | --- |
| 등록 원자성 | 생성 요청 저장이 실패해도 `Monster`가 남았습니다. | Job 저장이 실패하면 `Monster`도 롤백됩니다. |
| 동시 선점 | 두 Worker가 같은 요청을 조회하고 중복 생성했습니다. | 같은 후보를 읽은 두 Worker 중 하나만 선점에 성공합니다. |
| Worker 무응답 뒤 복구 | 요청 행을 삭제한 뒤 예외가 발생하면 복구할 행이 남지 않았습니다. | 응답이 없는 `RUNNING` 작업을 기한 만료 후 재선점하고, 새 token만 결과를 반영합니다. |
| 결과 연결 | 요청 ID와 Monster ID를 어긋나게 두면 다른 `Monster`를 갱신했습니다. | Job의 `monster_id`로 지정한 대상에만 결과를 저장합니다. |
| 스케줄러 지속 | 첫 작업의 예외 이후 특정 후속 작업이 완료되지 않았습니다. | 한 작업이 실패한 뒤에도 특정 후속 Job이 완료됩니다. |

Worker 무응답 복구 테스트에서는 선점한 뒤 완료·실패를 기록하지 않는 DB 상태를 만들었습니다. 이후 테스트용 `Clock`을 전진시켜 처리 기한 만료와 재시도를 재현했습니다. 이전 token의 완료 요청이 거부되고, 새 token으로 완료한 결과가 저장되는지까지 확인했습니다.

## 일반 테스트 33건과 회귀 테스트 5건 통과

2026년 10월 15일에는 Java 21과 MySQL 9.2.0의 전용 테스트 DB를 사용해 일반 테스트와 회귀 테스트를 실행했습니다.

| 구분 | 실행 | 실패 | 오류 | 건너뜀 |
| --- | ---: | ---: | ---: | ---: |
| 일반 테스트 | 33건 | 0건 | 0건 | 0건 |
| 신뢰성 회귀 테스트 | 5건 | 0건 | 0건 | 0건 |
| 합계 | 38건 | 0건 | 0건 | 0건 |

다섯 신뢰성 조건과 함께, 이미지 저장이 실패하면 Job의 성공 전환도 롤백되는 조건을 확인했습니다. Job 상태만 성공으로 남고 이미지가 없는 상황을 막기 위한 검증입니다.

이전에 실패 기록이 있던 스케줄러의 후속 Job 완료 조건도 이 실행에서는 통과했습니다. 다만 당시 실패 원인은 아직 확인이 필요합니다. 실행 명령과 집계, 이전 실패 기록은 [현재 검증 상태](../05-regression-verification/README.md#현재-검증-상태)에 정리했습니다.

## 별도 JVM에서 이미지 생성 작업 300건 완료

2026년 10월 18일에는 웹 서버, Worker, 측정 프로그램(Measurement)을 각각 별도 JVM으로 실행했습니다. Measurement는 HTTP로 작업을 등록하고 상태를 조회하며, MySQL에서 접수한 Job과 생성 결과를 대조합니다.

새 측정 전용 DB를 사용했고, 시작할 때 `Monster`와 Job 테이블이 모두 비어 있는 것을 확인했습니다. 실행 조건은 다음과 같습니다.

| 항목 | 실행 조건 |
| --- | --- |
| 실행 환경 | Apple M3, 논리 CPU 8개, 메모리 8GiB, macOS 15.2 |
| Java·DB | Java 21.0.5, 로컬 MySQL 9.2.0 |
| 프로세스 | 웹 서버·Worker·Measurement 각각 독립 JVM, Worker 프로세스 1개 |
| HTTP 등록 | 총 300건, 등록 동시성 35 |
| 이미지 생성 | Worker 동시 처리 상한 8, 모의 Generator 지연 5초 |
| 선점·재시도 | 처리 기한 30초, 최초 실행을 포함해 최대 3회, 재시도 간격 1초 |
| Worker 조회 | Polling·만료 복구 간격 각각 100ms |
| 측정 | 제한 시간 10분, HTTP·DB 관찰 간격 1초 |

Worker 동시 처리 상한 8과 모의 생성 지연 5초는 이번 측정의 실행 인자로 지정했습니다. HTTP 등록 동시성 35는 측정 프로그램이 동시에 보낼 수 있는 등록 요청의 상한입니다. 일정한 초당 요청 수를 유지하는 방식으로 실행하지는 않았습니다. 상세 JVM·DB 설정과 실제 실행 인자는 [실행 기록](../06-final-300-job-measurement/results/04a01500-aafe-44be-a619-9c4a1ad2b72b/README.md)에 남겼습니다.

[측정 요약](../06-final-300-job-measurement/results/04a01500-aafe-44be-a619-9c4a1ad2b72b/summary.json)의 결과는 다음과 같습니다.

| 항목 | 실제 결과 |
| --- | --- |
| HTTP 202 접수·고유 Job ID | 각각 300건 |
| HTTP 실패·중복 Job ID | 각각 0건 |
| `SUCCEEDED` | 300건 |
| `FAILED`·미종결·누락 | 각각 0건 |
| 결과 오연결·이미지 없는 성공 | 각각 0건 |
| 재시도 Job·추가 선점 시도 | 각각 0건 |
| 전체 완료 시간 | 193.639초 |
| 최종 상태 관찰까지의 시간 | 194.127초 |

전체 완료 시간은 측정 프로그램의 접수 시작부터 마지막 Job의 `finishedAt`까지로 계산했습니다. 모든 Job의 종결을 확인하고 관찰을 끝낸 시점까지는 194.127초가 걸렸습니다. 작업의 완료 시각과 측정 프로그램의 관찰 종료 시각을 나눠 기록한 것입니다.

제한 시간에 `PENDING`이나 `RUNNING`으로 남으면 미종결, HTTP 202로 접수한 Job 자체를 DB에서 찾지 못하면 누락으로 집계합니다. 이번 실행에서는 모두 0건이었습니다.

[작업별 CSV](../06-final-300-job-measurement/results/04a01500-aafe-44be-a619-9c4a1ad2b72b/jobs.csv) 300행의 ID, 상태, 이미지와 시도 횟수를 다시 집계하고, 백분위수와 요약 수치를 포함한 36개 대조 항목이 모두 일치하는 것을 확인했습니다. DB에서도 Job·Monster·성공 결과가 각각 300건이고, 프롬프트에 대응하는 이미지가 저장된 것을 확인했습니다. 상세 대조 결과는 [CSV 검증 기록](../06-final-300-job-measurement/results/04a01500-aafe-44be-a619-9c4a1ad2b72b/verification.json)과 [DB 검증 기록](../06-final-300-job-measurement/results/04a01500-aafe-44be-a619-9c4a1ad2b72b/database-verification.json)을 참조합니다.

재시도는 `attemptCount >= 2`인 Job을 기준으로 집계했습니다. 모든 Job의 선점 횟수는 1회였지만, 이 기록만으로 Generator 호출 자체가 정확히 한 번이었다고 판단하지는 않습니다.

## HTTP 접수 p95 160ms와 작업 대기 p95 178.087초

접수와 작업 완료까지의 시간을 살펴보기 위해 HTTP 등록 응답, Job 대기, Job 처리 시간을 나눠 측정했습니다. 아래 단위는 모두 ms입니다. p50·p95·p99는 측정값을 정렬했을 때 각각 50%·95%·99% 위치의 값이며, nearest-rank 방식으로 계산했습니다.

| 지표 | 계산 기준 | p50 | p95 | p99 |
| --- | --- | ---: | ---: | ---: |
| HTTP 등록 응답 | 등록 요청 시작부터 응답까지 | 20 | 160 | 173 |
| Job 대기 | `startedAt - createdAt` | 91,719 | 178,087 | 188,270 |
| Job 처리 | `finishedAt - startedAt` | 5,007 | 5,016 | 5,038 |

HTTP 등록 응답의 p95는 160ms였고, Job 대기의 p95는 178.087초였습니다. 생성 작업 처리 시간의 p95는 5.016초였구요. 300건을 접수하는 동안 Worker가 한 번에 실행할 수 있는 작업은 최대 8개였으므로, 실행 차례가 오지 않은 Job은 DB에서 기다렸습니다.

관측한 최대 `PENDING`은 295건이었습니다. 이 값은 1초 간격의 관찰에서 포착한 대기 작업 수입니다. 관찰 사이에 더 많은 작업이 대기했는지는 확인하지 못했습니다.

그러니까 HTTP 접수 응답 시간과 이미지 생성 결과를 받기까지의 시간은 함께 봐야 합니다. 이번 실행에서도 접수 응답 뒤에 작업 대기가 길게 이어지는 것을 확인했습니다.

## 300건 기본 검증 통과와 남은 확인 범위

이번 실행은 정해둔 300건 기본 검증 조건을 모두 통과했습니다. 접수한 작업이 최종 성공 상태에 도달했고, 누락과 결과 오연결도 발견되지 않았습니다.

이 결과는 모의 Generator를 사용하는 로컬 환경의 단일 정상 부하 실행에서 확인했습니다. 실제 AI 생성 성능과 최대 처리량, 과거 운영 장애의 해결 여부는 이번 측정으로 확정할 수는 없습니다.

Worker 무응답 뒤 복구와 오래된 결과 거부는 앞의 회귀 테스트에서 확인한 조건입니다. 300건 측정에서는 작업이 모두 완료된 뒤 측정용 세 JVM과 임시 MySQL을 종료했습니다. 이는 측정 환경의 정리 절차였으며, 처리 도중 JVM을 종료하고 재시작해 작업을 복구하는 실험은 아직 남아 있습니다.

추가 부하 측정은 아직 실행하지 않았습니다. 다음 측정에서는 다른 조건을 유지한 채 총 요청 수를 늘려 작업 대기 시간과 최대 `PENDING`, 전체 완료 시간의 변화를 비교하려고 합니다. 구체적인 확대 기준은 [측정 범위](../06-final-300-job-measurement/README.md#측정-범위와-확대-기준)를 따릅니다.

다음 [⑤ 주의할 점](./05-limitations.md)에서는 이번 구현의 보장 범위와 Polling 비용, 처리 기한과 동시성 상한을 사용할 때의 제약을 정리하겠습니다.
