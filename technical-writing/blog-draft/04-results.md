# ④ 달라진 점과 근거: 해 보니 무엇이 달라졌나요?

구현의 변화는 요청 등록부터 결과 반영까지 판단할 정보를 DB에 남겼다는 점입니다. 최소 구조에서는 요청 행의 조회와 삭제를 중심으로 처리했습니다. 개선 구조에서는 등록 트랜잭션, 상태 전이, 실행 권한과 처리 기한을 기준으로 다음 동작을 결정하도록 했습니다. 이 차이를 확인하기 위해 실패 재현 테스트와 회귀 테스트를 같은 다섯 조건으로 연결했습니다.

## 같은 조건을 RED와 GREEN에서 비교했습니다

RED 테스트는 원하는 신뢰성 조건을 assertion으로 작성하고, 최소 구조가 이를 지키지 못하는 상황을 재현합니다. 예를 들어 요청 등록 실패 후 Monster가 남지 않아야 한다고 검사하거나, 두 Worker가 같은 후보를 읽었을 때 한 번만 생성해야 한다고 검사합니다.

여기서 실패는 의도한 불변식 assertion의 실패여야 합니다. DB에 접속하지 못했거나 Spring Context가 시작되지 않은 결과는 문제를 재현한 근거로 사용하지 않습니다. GREEN 테스트는 개선 구조에서 대응하는 조건을 다시 검사합니다.

| 신뢰성 조건 | 최소 구조의 실패 재현 | 개선 구조에서 검사하는 조건 |
| --- | --- | --- |
| 등록 원자성 | 생성 요청 저장 실패 후 Monster만 남습니다. | Job 저장이 실패하면 Monster도 롤백됩니다. |
| 동시 선점 | 두 Worker가 같은 요청을 조회하고 중복 생성합니다. | 같은 후보의 조건부 UPDATE는 하나만 성공합니다. |
| Worker 무응답 뒤 복구 | 처리 전 삭제 후 예외가 발생하면 요청 행이 남지 않습니다. | 기한 만료 후 재선점하며, 새 token만 결과를 반영합니다. |
| 결과 연결 | 요청 ID와 Monster ID를 어긋나게 두면 잘못된 대상을 갱신합니다. | Job의 명시적인 `monster_id`로 결과를 연결합니다. |
| Scheduler 지속 | 첫 작업의 예외 이후 특정 후속 작업이 완료되지 않습니다. | 실패 처리 뒤 특정 후속 Job이 실제로 완료되는지 검사합니다. |

이 대응은 [05단계의 회귀 검증](../05-regression-verification/README.md)에 정리돼 있습니다. Worker 무응답 복구 테스트는 선점 후 응답이 없는 DB 상태를 만들고, 테스트 Clock을 전진시켜 만료와 재시도를 재현합니다. 실제 JVM을 종료하는 테스트와는 검증 범위를 구분합니다.

## 현재 확인된 기록과 다시 확인할 결과가 있습니다

2026년 9월 14일의 문서에는 RED 다섯 건의 의도한 실패와 GREEN 다섯 건의 통과가 기록돼 있습니다. 다만 로컬에 남아 있는 9월 15일 회귀 보고서는 등록 원자성·동시 선점·무응답 복구·결과 연결 네 건의 통과와 Scheduler 테스트 한 건의 실패를 기록합니다. 실패 내용은 후속 Job이 제한 시간 안에 완료되지 않았다는 assertion입니다.

**보류:** 현재 코드에서 다섯 GREEN 조건이 모두 통과했다고 결론 내리지는 않습니다. 회귀 테스트를 다시 실행하고 Scheduler 실패 원인을 확인한 뒤 검증 기록을 갱신해야 합니다. 최신 판단은 [현재 검증 상태](../05-regression-verification/README.md#현재-검증-상태)를 기준으로 합니다.

따라서 현재 초안에서는 추가한 구현 규칙과 남아 있는 검증 기록을 설명합니다. 실패를 모두 해결했다는 결론은 다섯 조건의 통과를 재확인한 뒤 작성합니다.

## 300건은 실제 프로세스 경계에서 확인할 기본 조건입니다

통합 테스트에서 제어한 조건과 별도 JVM의 동작은 각각 확인해야 합니다. 이를 위해 Web·Worker와 별도로 실행하는 Measurement 프로그램을 준비했습니다. 이 프로그램은 HTTP로 요청을 등록하고 상태를 조회하며, MySQL에서 접수한 Job과 결과를 대조합니다.

**채택:** 정상 부하 조건에서 HTTP 요청 300건을 기본 검증으로 측정합니다. 현재 실제 측정과 결과 파일 생성은 미실행입니다. 아래 표는 측정 결과가 아니라 실행 후 확인할 기준입니다.

| 항목 | 기본 검증 기준 | 현재 결과 |
| --- | --- | --- |
| 접수 | HTTP 202 접수 300건, 고유 Job ID 300개입니다. | 미측정 |
| 완료 | 제한 시간 안에 `SUCCEEDED` 300건입니다. | 미측정 |
| 실패·미종결·누락 | 각각 0건인지 확인합니다. | 미측정 |
| 결과 연결 | 오연결과 이미지 없는 성공이 0건인지 확인합니다. | 미측정 |
| 재시도 | 정상 부하에서 0건을 기대하며, 발생 시 원인을 확인합니다. | 미측정 |
| 전체 완료 시간 | 접수 시작부터 모든 접수 Job의 최종 상태 도달까지 기록합니다. | 미측정 |

제한 시간이 끝났을 때 `PENDING`이나 `RUNNING`인 작업은 미종결입니다. 접수한 Job 자체가 DB에 없는 누락과 구분합니다. 완료·실패·미종결·누락을 함께 기록해야 접수한 작업의 최종 상태를 설명할 수 있습니다.

기본 검증이 통과하면 먼저 총 요청 수를 늘리고, 이후 필요하면 총 요청 수를 고정한 채 HTTP 동시성을 늘립니다. 다른 조건을 유지하면서 작업 대기 시간, 최대 PENDING, 재시도율과 전체 완료 시간의 변화를 비교합니다. 여기서 재시도율은 `attemptCount >= 2`인 Job 수를 고유 접수 Job 수로 나눈 값입니다. 이 횟수는 선점 기록이며 실제 Generator의 호출 횟수와 구분합니다. 구체적인 실행 조건과 결과 형식은 [06단계](../06-final-300-job-measurement/README.md)를 따릅니다.

정상 부하에서 300건이 완료됐다는 결과는 그 실행 조건의 접수·처리를 확인하는 근거입니다. Worker 무응답 뒤의 복구나 오래된 결과 거부는 별도의 장애 재현 테스트로 설명합니다. 또한 모의 Generator를 사용하므로 실제 AI 모델의 처리량으로 해석하지 않습니다.
