# Session

### Session이란?

Session은 여러 HTTP 요청에 걸쳐 필요한 사용자별 상태를 이어서 사용하는 방식이다.
여기서 Server Session은 서버가 로그인 상태 등의 데이터를 저장하고, 세션 ID로 해당 데이터를 찾는 방식을 뜻한다.
HTTP는 무상태지만 애플리케이션은 Server Session으로 상태를 관리할 수 있다.

### 동작

#### 1. Session ID

- 로그인 시 서버는 세션 데이터를 저장하고 세션 ID를 발급한다.
- 서버가 응답의 `Set-Cookie`로 ID를 전달하면, 브라우저는 이후 요청의 `Cookie`에 ID를 담아 보낸다.
- 서버는 ID로 세션 데이터를 조회한다. Cookie의 세션 ID와 서버의 세션 데이터는 서로 다르다.

#### 2. Multi-Server Problem

1. 사용자가 서버 A에서 로그인하고, A의 메모리에 세션이 저장된다.
2. 다음 요청이 서버 B로 전달된다.
3. B에는 해당 세션 ID의 데이터가 없어 로그인 상태를 확인할 수 없다.

다중 서버에서도 로그인이나 장바구니 상태를 유지하려면 어느 서버가 요청을 받아도 필요한 세션을 사용할 수 있어야 한다.

#### 3. Session Clustering

- 서버 사이에 세션 데이터를 복제한다. Tomcat의 `DeltaManager`는 모든 노드에, `BackupManager`는 백업 노드 하나에 복제한다.
- 서버가 바뀌어도 복제된 세션을 사용할 수 있지만, 복제 트래픽과 직렬화·설정 비용이 든다.

#### 4. Sticky Session

- 로드 밸런서가 같은 사용자의 요청을 같은 서버로 보내 로컬 세션을 계속 사용하게 한다.
- 세션 자체를 공유하지 않으므로 해당 서버에 장애가 나면 다른 서버에서 세션을 찾지 못할 수 있다.

#### 5. Shared Session Store

- 모든 서버가 Redis 같은 공통 저장소에서 세션을 조회하고 갱신한다. Spring Session은 `HttpSession`을 Redis에 저장할 수 있다.
- 요청이 어느 서버로 가도 같은 세션을 찾지만, 네트워크 조회와 저장소 운영 비용이 생긴다. 저장소 장애에도 대비해야 한다.
- 기존 Server Session을 유지하면서 다중 서버로 확장한다면 공유 저장소가 적합한 선택이다.

#### 6. JWT and REST

- 서명된 JWT를 매 요청에 보내고 각 서버가 검증하면 로그인 확인을 위한 서버 세션 공유가 필요하지 않을 수 있다.
- JWT만으로 장바구니 등 모든 상태가 무상태가 되지는 않는다. 즉시 로그아웃이나 권한 변경 반영에는 별도 상태 관리가 필요할 수 있다.
- 세션 클러스터링, 스티키 세션, 공유 저장소는 세션 불일치를 해결하지만 REST의 무상태 제약을 충족시키지는 않는다.
